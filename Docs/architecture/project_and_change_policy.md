# Project and current-contract policy

Status: normative.

## Portable project contract
<!-- decision-owner: persistence.portable-project-contract -->

The current schema version is 23. The source document requires one named Input Transform. The simulation request requires one independently authored Output Signal resolved by `screen-color`. The device document requires one stable Panel-owned Color Mode interpretation and carries the complete materialized optical-cover profile, including its required nested anti-glare microtexture realization and bounded emission-glow profile, fixed spatial-uniformity profile and temporal-emission profile in addition to the LCD profile. The glow block explicitly stores character strength, gain, one physical radius and a panel-white-relative luminance threshold. The microtexture block explicitly stores character strength, RMS slope, physical correlation length in micrometers, anisotropy and stable seed; none may be supplied by a preset or inferred during opening. The current shot document carries the complete authored synthetic-HDR environment profile, including its required spherical-pattern identity, explicit X/Y rotations and ACEScg radiance values. Bundled device, cover and environment ids are non-authoritative authoring provenance only; normal opening and evaluation never consult those catalogs.

The portable project is a `.screensim` package directory with one strict root manifest and separate owner documents for sources, device profiles, camera/screen tracks and simulation shots. SQLite is not a project format.

The current package root is `project.json`. It references exactly one source document, device document, camera document, sensor document, screen document and shot document through portable relative paths. Each document carries its one exact schema name and version. The source document references its packaged media resource separately; no resource path may overlap a document path. Creation writes a complete package to a private sibling staging directory and publishes it by one rename only after every document and the source resource have been written. It never overwrites an existing package.

Project documents contain portable relative references and stable opaque ids. Machine-specific media associations, recent projects, window state, decoded frames, thumbnails and GPU caches live outside the project and are never authoritative. A missing external association is visible and is never replaced by a same-name or nearby file.

Normal open validates without writing. Each document has one current schema and version. Unknown versions, unknown fields, missing required values and invalid references fail explicitly.

The strict `Scenes.v28.json` library owns stable local Production, Episode and Shot branches plus one placement for every `ScreenSimulation.SavedScene.v26` record. A Production owns `seasonSlug` only as an attribute, never as a branch. An Episode owns ordered Shots and every Shot owns an immutable monotonically allocated three-digit scene ordinal; removing or moving a scene never releases an allocated ordinal. Scene presentation is alphabetic by shelf name with UUID as the deterministic tie break, independently of that ordinal. A scene is present exactly once, either below one Shot or in the explicit unclassified collection. Moving a scene is one atomic library mutation; entering a Shot allocates its next ordinal, adopts `<shot name>_<ordinal as three digits>` as the Scene name and moving within the same Shot does not mutate it. A placed Scene name is read-only until the Scene returns to unclassified. Associating an Episode adopts its exact external slug as its name; associating a Shot adopts its external canonical name and renames all its placed Scenes from that name and their existing ordinals. Associated Episode and Shot names are read-only until their branch becomes free. Renaming a free Shot likewise refreshes the derived names of its placed Scenes. The scene snapshot, thumbnail, generated Environment ownership and active-scene identity remain unchanged by tree movement or derived renaming.

Scene recovery points use the strict `Autosave.v25` collection and `ScreenSimulation.SceneAutosave.v3` records embedding the same current `SavedScene.v26` snapshot; older autosave collections are never read or upgraded during normal operation.

Global Library text and numeric editors own incomplete keyboard text locally and submit one complete candidate only on Return or focus loss. Domain validation and persistence never run against each intermediate keypress. Pickers and toggles remain complete candidates and commit immediately.

Active Saved Scene text and numeric editors follow the same keyboard boundary. A valid candidate submitted by Return or focus loss is one scene-authoring transaction and immediately replaces the active strict shelf snapshot and thumbnail; incomplete keystrokes never reach Application, evaluation or persistence. Choices, toggles, buttons and keyframe actions commit immediately. Sliders and Viewer gestures may publish transient resolved candidates while the gesture is active, but only the final gesture value is persisted. There is no dirty active-scene draft, manual Update action or Save/Discard navigation branch. Undo and Redo automatically persist the restored complete capture, and Render re-resolves the current stored record before enqueue.

A Saved Scene rename is an immediate shelf-record mutation, not unsaved scene authoring. Return, focus loss, leaving the shelf presentation or invoking a contextual scene action first commits the trimmed nonempty name atomically. Navigation and normal application termination cannot leave a visually edited draft as the apparent name; reopening reads the committed name, and contextual Render resolves the scene again after committing so its seeded output name is current.

Scene settings transfer uses one strict versioned workstation clipboard document. Copy explicitly includes any subset of the Application-published top-level inspector cards; Device geometry and Camera geometry are separately selectable blocks rather than implicit members of their parent cards. Paste presents every block, disables blocks absent from the clipboard, and requires a second explicit confirmation before replacing the selected destination values. Control ownership is the conflict-checked union of the exact Application-published source and destination presentations, so a control conditionally visible only under the source or destination representation—such as external-Environment exposure—retains its owning card without a host/UI lookup table. When the destination is the active Scene, its complete current capture is the destination state and already equals the automatically stored shelf authoring; Paste persists that state plus the selected replacements before reopening it. Unselected destination blocks, including fixed Device and Camera geometry and their typed animation, Scene identity, shelf name, tree placement, Shot ordinal and Viewer navigation remain unchanged. A selected block replaces both its fixed authored values and every typed animation track owned by that block; the current embedded tracking-camera animation belongs to Camera geometry. Unknown schemas, unknown fields, duplicate blocks and values that cannot satisfy the current Saved Scene contract reject the clipboard before Paste is offered. Generated Environment data copied with Entorno is materialized under the destination Scene identity.

A contextual Saved Scene reset requires explicit confirmation and preserves exactly the Scene identity, shelf name, tree placement and Shot ordinal together with its complete Source route and interpretation/placement and its complete Reference selection/resource. Every other authored value is rebuilt from the same current Global Library and Application-owned defaults used for a new Scene: selected profiles, fixed and model overrides, Environment, camera/tracking import, delivery, Preview selection, current frame and Viewer navigation are reset. For the active Scene, the preservation source is its complete automatically stored capture; for an inactive Scene it is the stored snapshot. The replacement is one atomic shelf mutation and one Undo operation, removes any generated Environment asset ownership, and reopens an active Scene from the resulting stored record. It never changes the workstation contract or runs as startup migration.

The workstation scene shelf is separate from the portable `.screensim` project. Its current `ScreenSimulation.SavedScene.v26` records live under Application Support. The current Global Library is the strict `GlobalLibrary.v17.json`; earlier filenames and schemas are not opened, repaired or migrated by normal startup. A scene stores exactly one stable identity for every selected internal simulation-profile family—Device, Cover Glass, Camera/Sensor, Lens, procedural Environment and every later family—together with only explicit fixed overrides. All those identities resolve through one typed immutable snapshot of the workstation Global Library. Every current Camera record owns `vfx-2d-dof` as its default Lens evaluation model; a scene may explicitly override it with `thin-lens`, and duplication preserves that authored override verbatim. Bundled definitions are seed input used only to create initial library records or an explicitly new record; after that boundary a locked seed record and a user-created record have identical identity, resolution, validation and evaluation semantics. No host or Application path may consult a compiled seed catalog as a second runtime authority or substitute another item when an identity is missing.

A one-way Global Library version migration preserves every existing user-authored item in every collection without changing its stable identity, authored value, collection order, lock state or references. A new schema may append new locked seeds or explicitly transform affected fields, but it cannot reconstruct the document from the current built-in catalog, silently omit user records or replace them by name. Deletion or semantic replacement of identified user items requires a separate explicit user decision. Owning migration tests populate every collection with user-authored records and compare them unchanged after conversion in addition to checking the intended schema delta.

A manual edit creates or replaces that parameter's override; Reset removes it. Cards, numeric fields, selectors and interactive Setup/Focus/Environment/Match gizmos all submit the same stable parameter-id edits to one scene-authoring transaction boundary. An editor receives only the resolved values it needs and returns only the parameter ids and proposed values it changed: it cannot inspect whether a value came from a profile, override or track, and the scene cannot branch on which editor produced the edit. A multi-parameter gesture commits atomically as one edit and one Undo group. Its transient candidate may be presented while dragging, but only the scene transaction owns the resulting override set. An explicitly edited value remains an override even when it numerically equals the current profile default; only Reset removes that ownership. Undo and Redo restore both values and override presence. On Open and evaluation, Application obtains the current Global Library definition selected by each stable id, then applies the fixed overrides. Values without an override therefore follow that current definition; the scene never embeds a second dense selection or a complete profile snapshot. Persisted override ordering is canonical serialization only and has no semantic authority: Application materializes a representation-selecting control before the dependent values expressed in that representation. In particular, Camera Geometry applies `geometry-mode` before the saved Free position and rotation so entering Free cannot replace the persisted pose. Every successfully committed Global Library edit invalidates the complete inherited profile layer of the active scene, irrespective of which library family changed. Application reads one new complete library snapshot, resolves every stored profile identity together, reapplies the scene's explicit overrides and publishes one rebuilt scene; it never patches only the edited field or retains a cached definition from the prior library revision. If any required identity or association no longer resolves, the active scene remains unchanged and the edit failure is explicit. Already frozen Render Queue attempts remain immutable. Application freezes the resulting complete immutable request before evaluation, so physical phases never perform profile lookup. The current animation-bearing Saved Scene contract owns the separately typed embedded 3D record, the separately typed materialized Fusion Tracker camera-or-Device pose record and one `SceneAnimation.v1` Application-parameter document. Its first and only current scalar track is `simulation-opacity`; its exact-time semantics and zero shortcut are owned by `scene.parameter-animation`. A later parameter may enter this collection only when its semantic owner publishes the typed capability and Saved Scene advances together with its evaluator and tests. The portable v22 project does not claim this workstation-only collection. A missing selected identity, dangling association between profile families, duplicate parameter override or override incompatible with the current owner-published bounds rejects Open explicitly. This rule is limited to the workstation Saved Scene and does not alter the portable `.screensim` documents described above, which remain complete materialized project contracts. Global Library resources that are not simulation profiles—external test media and complete output presets—remain complete library records; bundled records are still seeds rather than a parallel runtime catalog.

Source media, reference media and an authored external HDRI are the only permitted external scene-file dependencies and retain exact absolute paths while available. Source has exactly one active authored route: external media or one selected synthetic pattern. Explicitly removing an available external Source closes that media and activates the already selected synthetic pattern through the same canonical synthetic-source route; it does not retain a hidden media session, placeholder or parallel source. A missing, moved or undecodable external file never blocks workstation Saved Scene Open and never causes path search or same-name substitution. During materialization of the active scene, an unavailable Source is discarded and replaced by the stable initial synthetic pattern used by a new scene, an unavailable Reference is discarded to `None`, and an unavailable external Environment is discarded to the scene's selected procedural Environment profile with the explicit `environment-image` override removed. These are normal authored inputs, selected by stable identity rather than catalog order; they do not create placeholders or alternate rendering routes. One post-open modal lists every discarded dependency. Opening remains read-only for the shelf record; the next successfully committed active-scene edit persists the complete cleaned authoring together with that edit. Structural scene errors, unresolved internal profile identities and malformed authored resource records still reject Open transactionally without modifying the active scene. Any imported camera animation, point cloud or geometry becomes ordinary scene-owned authoring at the import boundary and is embedded completely, without retaining or reopening the importer file. Explicitly removing an imported camera animation first resolves the current frame through Application, replaces only the selected camera's curve with that single static pose, and preserves its focal, gate, distortion, point clouds, geometry, visibility and metric calibration; this confirmed edit is one Undo operation and is persisted immediately through the active-scene transaction. Every compact Scene row whose stored snapshot owns that authoring displays the explicit `3D importado` state and its own removal control. Confirmed complete removal targets that exact Scene, discards its complete imported camera, point-cloud, mesh, visibility and metric-calibration record, and exposes its independently authored manual camera. An inactive Scene uses its stored snapshot; the active Scene uses its complete current capture. The replacement is one atomic shelf mutation and one Undo operation, and an active Scene is reopened from the resulting stored record. A generated Environment also remains scene-owned under Application Support: one stable filename belongs to one scene, an update overwrites it atomically, a duplicate receives a copied generated asset with a new scene identity, and deletion removes it. Media timing stores frame-rate numerator and denominator explicitly. A normal scene-library load accepts only that exact current contract and is byte-for-byte read-only. When a persisted workstation contract advances, its named one-shot maintenance migration operates only on the explicitly selected source, first creates and verifies a timestamped byte-identical backup beside that source, refuses an existing destination, materializes every newly required value from authoritative prior data, validates all records, and publishes the complete new document atomically. A migration that cannot create or verify the backup cannot publish its destination. The application never keeps the old reader as a fallback and never infers a missing value during Open.

Render Queue is separate workstation state at `Application Support/SCREEN-SIMULATION/RenderQueue/RenderQueue.v15.json`. Its strict `ScreenSimulation.RenderQueue.v15` document owns a value copy of the Saved Scene authoring at enqueue time—its selected profile ids, fixed overrides, tracks and resources—plus generated Environment bytes, the explicit frozen Preview or Final mode, composition, Spill delivery mode, resolved render raster, Motion Blur mode, authored output base name and free version suffix, output configuration, exact destination and single- or two-media manifest, optional Final Fusion-composition configuration, policy, lifecycle state, terminal attempt timing and paused state. Preview is one baked Reference + Device + Spill result and may carry WIP Review. Final excludes Reference from its media and publishes Device + Spill either combined or as two alpha-bearing media; when Fusion is enabled, its package uses the combined topology and writes only the complete Device medium plus composition and metadata. Presets only seed these editable fields. Later scene edits or another current UI selection cannot change that job. At the beginning of each render attempt, its isolated Application workspace resolves the current internal definitions for the job's stored profile ids exactly once and freezes that materialized attempt before evaluating frames. Requeueing at a later time may therefore observe updated defaults of those same ids, but never a different id or a later override from the shelf scene. A missing stored identity fails the attempt explicitly. The queue is not part of any Saved Scene or portable project. A job observed as rendering when the process ends is explicitly restored as pending with an interruption detail and no terminal timing; it never resumes automatically. Queue updates write atomically after every lifecycle mutation. Every completed, failed or cancelled attempt retains its nonnegative total wall time and, when at least one frame completed, its average wall time per completed frame. Any inactive record may be removed explicitly. The bulk `Limpiar terminados` action removes every terminal record—completed, failed or cancelled—together. Neither action touches generated output files; pending and rendering records are retained. Earlier queue schemas and filenames are not opened, defaulted or migrated by startup.

An optional Saved Scene 3D-authoring record is complete only when it embeds the typed camera tracks, point groups and polygon geometry plus selected camera, selected point group, independent point/geometry visibility, visible auxiliary meshes and the authored metres-per-source-unit scale. Normal Open never invokes an importer or guesses a unit, camera, point group or geometry role.

## Shot Manager workstation association
<!-- decision-owner: scene.shot-manager-association -->

A local Production is either manual or owns one strict read-only Shot Manager association. Screen Simulation consumes a structural projection from one file named exactly `production.json`: if the required Production, Episode, Shot, Workstream and folder fields are decodable, their values are authoritative. It neither requires nor interprets a Shot Manager schema number and ignores producer-owned fields outside that projection, so an unrelated producer-schema advance cannot force a coordinated Screen Simulation release. Initial association requires its stable `productionId`, real containing root, production and season slugs, every Episode's required canonical relative `pathSegments`, and every explicitly selected Workstream/folder/suffix destination in one atomic value. Screen Simulation requests and persists its `render` and `comps` destinations together on every new association or explicit replacement; persisted destination roles remain independently usable, so absence of a role that is not needed by the current operation does not invalidate the entire library. Selecting a new association whose `productionId` already belongs to a local Production is a normal reconnect of that entry and cannot append a duplicate; if legacy state contains more than one exact match, the user explicitly chooses the local Production to reconnect. A normal reconnect accepts only the same `productionId` and atomically refreshes the root, slugs, exact destination spelling and suffixes together with every still-resolving Episode and Shot reference, including each resolving Episode's complete `pathSegments`. An absent, unreadable, malformed or destination-incomplete candidate changes no persisted value and does not block an already associated render. A valid same-Production catalog may free a missing Episode and all its Shots, or one missing Shot, while retaining its inactive external reference and last authoritative path; the same unmodified identity may reactivate only within that same Production. An explicit reassociation may adopt another `productionId` after choosing both destinations again; it frees every Episode and Shot and never infers a new association from names, slugs, order or position.

Every local Episode is free or stores the associated Production identity plus exact external Episode id, order, slug and complete `episodePathSegments` copied from the producer's `pathSegments`. Every local Shot is free or stores that same Production identity plus exact external Shot id and canonical name, and can be associated only below its exact external Episode. Free branches use only local naming and routing. Opening an editable Render draft for an associated Scene seeds its destination from the `render` role and its output identity from `<canonicalName><folderSuffix>_<scene ordinal>`; this applies both to a direct Scene render and to `Renderizar la escena actual…` from a prior job. Browse may explicitly replace that draft destination without mutating the Shot Manager association, and the Queue freezes the resulting authored destination. An associated render freezes one coherent Production/Episode/Shot/destination generation and resolves its managed default as `<root>/<episodePathSegments...>/<workstream>/<folder>`. Production/season slugs, Episode order, Episode slug, names and presentation position never participate in route construction. A disconnected association uses the persisted path segments unchanged. If the root is missing, the user may explicitly choose another existing root without a live JSON. Missing persisted subdirectories may be created additively one safe segment at a time; an empty or unsafe authored segment, existing symlink, non-directory, root escape or collision fails explicitly. The consumer never writes, migrates, reserializes or repairs `production.json`, and never deletes, renames, replaces or empties Shot Manager structure.

The one-way `Scenes.v23.json` to `Scenes.v24.json` maintenance migration preserves every scene identity, authored snapshot, thumbnail and existing order exactly and places those scene ids in the explicit unclassified collection. It creates and verifies a byte-identical timestamped backup beside the selected v23 source before publishing a new destination, and normal startup neither opens nor migrates v23.

The one-way `Scenes.v24.json` to `Scenes.v25.json` maintenance migration preserves every Production, Episode, Shot, Scene, placement, ordinal, authored value, ordering and reference, changes each embedded snapshot from `SavedScene.v23` to `SavedScene.v24` and explicitly records no Fusion Tracker pose. The separately selected `RenderQueue.v10.json` to `RenderQueue.v11.json` migration performs the same exact snapshot change for every job without changing its identity, lifecycle, order, configuration or output manifest. Both verify byte-identical source backups before publishing; normal startup opens neither prior contract.

The one-way `Scenes.v25.json` to `Scenes.v26.json` and `RenderQueue.v11.json` to `RenderQueue.v12.json` maintenance migrations preserve every authored item, collection, identity, order, lock state and reference, change each embedded snapshot from `SavedScene.v24` to `SavedScene.v25`, and materialize the previous runtime authority exactly: a non-null Fusion Tracker pose selects `fusionTrackerClipboard`; otherwise `fusionComposition` is selected. Both verify byte-identical source backups before publishing; normal startup opens neither prior contract.

The selected `Autosave.v23` to `Autosave.v24` maintenance migration composes the prior no-Fusion-Tracker transformation for any retained `SavedScene.v23` recovery point, applies the same exact active-method mapping to every `SavedScene.v24` point, preserves every scene directory, revision, thumbnail, generated Environment, identity and ordering, and publishes `SceneAutosave.v2` with embedded `SavedScene.v25` only after verifying a byte-identical backup of the complete source tree. Normal recovery reads only the resulting current collection.

The selected `Scenes.v26.json` to `Scenes.v27.json`, `RenderQueue.v14.json` to `RenderQueue.v15.json` and `Autosave.v24` to `Autosave.v25` maintenance migrations preserve every authored item, identity, collection, order, lock state, lifecycle value, resource and reference. They advance every embedded snapshot from `SavedScene.v25` to `SavedScene.v26` and add exactly one `SceneAnimation.v1` opacity track at constant one with one deterministic stable keyframe identity at exact time zero. Each migration verifies a byte-identical source backup before publication; normal startup reads only the resulting current contract and never invokes these tools.

The selected `Scenes.v27.json` to `Scenes.v28.json` maintenance migration preserves every authored Scene, Production, Episode, Shot, placement, ordinal, snapshot, collection, order and reference. For every persisted external Episode reference it requires one explicitly supplied `production.json` whose decodable `productionId`, Episode `id` and `pathSegments` provide the authoritative route; it does not inspect a Shot Manager schema number or derive a segment from order, slug, name or position. A missing, ambiguous or unsafe path rejects the complete migration. The migration adds only `episodePathSegments`, advances the Scene Library version, verifies a byte-identical source backup and publishes to a new destination; normal startup reads only v28.

## Portable materialized project contracts

The authored Recording selection is mandatory: exact codec profile id and finite Character. Application resolves the one Color-owned recording-output transform required by that profile; persistence cannot author a contradictory pair. Profile identity is never inferred from filename, extension, container, export format or raster values. Capture presets provide only the explicit initial recommendation for new authoring and never alter a persisted selection while opening.

Current camera intrinsics require the bounded lens veiling-glare fraction. It is
materialized authoring data like every other lens coefficient; a preset id can never supply it at
open or evaluation time.

Persistence validates document structure, stable opaque identifiers including full per-track keyframe uniqueness, portable paths, exact-time representation, ordering and cross-document references. Device documents carry the complete native raster and active physical dimensions in addition to native-primary and white-point chromaticities, angular response, residual-flicker period/amplitude/phase and optional analytic-banding period/duty/phase/amount. A bundled preset id may be recorded only as non-authoritative provenance; opening and evaluation consume the complete device document and never consult the catalog. Camera intrinsics documents carry every authored lens coefficient, emitter transmission, vignetting parameter and center/edge softness in micrometers explicitly; lens preset identity is likewise non-authoritative workstation provenance and never replaces those values. Sensor documents carry the native photosite raster, saturation exposure in lux-seconds, complete current photosite response, calibrated crosstalk and nonrecursive overflow-transfer profile and the exact global-shutter duration and motion-sample contract; shots reference that sensor and author the deterministic noise seed, optical ND, EI with its calibrated reference middle-gray exposure, explicit native-sensor white-balance gains, develop push/pull and one stable camera-output-transform identifier. Persistence validates their strict representation but does not resolve the transform catalog. The composition root translates them once into `screen-camera` and `screen-color` values; an unknown output identifier fails instead of selecting a display default. Persistence does not evaluate media, color, panel response, lens invertibility, camera projection, sensor response or simulation. The composition root performs one strict current-document translation into the owning domain types and validates those types before evaluation; those domains remain authoritative for their semantics.

During development, contract, profiles, fixtures, tests and renderer form one current world. A breaking change updates them together and may change every visual result. No earlier reader, evaluator, profile behavior, output result, alias, compatibility flag or version dispatch remains active.

When conversion is useful, an explicit one-way maintenance command operates on a disposable copy or explicitly selected package, writes the complete current representation and validates it. It is not callable from normal open/read/render paths. Once the current data has been updated, temporary conversion code is removed from the delivered runtime.

Build commit, OCIO library/config versions, GPU backend and project content hash may be recorded as provenance. Provenance never selects an earlier implementation.
