# Current system

Status: normative.

Application owns every phase boundary as a `PhysicalArtifactId`: the typed identity proves adjacency, while host adapters receive only its stable versioned string for presentation and serialization. Swift and the native bridge cannot declare, infer or reorder artifact identities. The CPU evaluator publishes a closed `PhysicalPipelineCpuArtifact`; sensor checkpoints contain the actual integer RAW artifact and expose their normalized code/clipping image only through a separately named diagnostic presentation view. RAW, Device signal and physical radiance are never stored in a field named ACEScg.

## Product boundary

The application consumes an explicitly interpreted animated raster and evaluates a physical fixed-pixel LCD through animated screen/camera geometry and phase-preserving photosite-footprint sampling. The FFmpeg adapter accepts the video and still-image formats enabled in the one shipped decoder configuration, including H.264 and ProRes. ProRes 4444 is a recommended high-quality production source, not an input restriction. OpenEXR sequences use the explicit OpenEXR adapter. No codec or container chooses color interpretation.

The current processing chain is:

```text
media source
→ explicit pixel decode interpretation
→ decoded source frame
→ explicit Input Transform into linear ACEScg
→ independently authored feeder Output Signal transform
→ typed nonlinear feeder signal
→ feeder placement into the selected target-device raster
→ Device Color Mode interpretation
→ colorimetrically declared, angle-dependent LCD emission
→ native panel subpixel structure
→ calibrated panel light spread
→ independently animated screen/camera projection
→ explicit optical-cover transmission and authored environment reflection
→ bounded VFX emission bloom and soft halo from resolved panel emission, with additive support outside the active panel outline
→ deterministic sensor-footprint and thin-lens integration
→ immutable linear ACEScg optical result in image-plane illuminance
  ├→ explicit optical-preview or still-output transform
  └→ exact global/rolling-shutter temporal integration
     → explicit photometric exposure, optical ND and shutter integration in lux-seconds
     → Bayer photosite charge, calibrated neighbour crosstalk and nonrecursive full-well overflow
     → full-well saturation, noise, gain and ADC quantization
     → single reference edge-directed Bayer demosaic
     → explicit native-sensor white balance
     → explicit EI middle-gray placement and develop push/pull
     → immutable linear ACEScg developed camera result
     → camera-authored rendering intent in linear ACEScg
     → explicit Color-owned recording-output transform
     → nonlinear float recording signal before quantization and subsampling
     → explicit Recording-owned encode/decode
```

Native output jobs keep codec and color encoding as separate authored choices. The current VFX movie masters are ProRes 4444 and ProRes 4444 XQ with one explicit Color-owned Log/Gamut selection. A capture preset may recommend a Log/Gamut as the initial value, but it neither restricts the catalog nor changes an existing authored choice. Application freezes the exact codec and stable Log/Gamut id in the immutable render job; the writer applies that OCIO transform and does not declare the result as Rec.709. ACEScg and ACES2065-1 remain explicit OpenEXR output contracts rather than implicit ProRes interpretations.

Render Queue also owns one explicit `Fusion Scene Package` output type. It evaluates the immutable Saved Scene through a headless Device-VFX route in the same physical evaluator; Preview, Reference and the ideal Source are not radiometric inputs to this export. The package writes RGBA half-float OpenEXR in scene-linear ACEScg, where RGB is the complete additive physical Device contribution including exterior glow/spill and A is the independent achromatic occlusion matte. RGB is preserved when A is zero. The portable generated job directory is `<jobName>_FusionScene/{media,fusion,metadata}` and its EXR, comp and metadata paths are relative. When present, the Fusion reference Loader deliberately names the original absolute source path: the reference remains an explicit external dependency and is never copied into the package. It places one fixed rectified frontal Device at the origin on a padded ImagePlane3D. Fusion derives that plane's base Y extent from the EXR aspect, so export converts the physical padded width and height to ImagePlane3D scale exactly once rather than applying the texture aspect twice. Camera3D receives the explicit horizontal angle of view together with focal length and the user film gate, reconstructs the authored camera, delegates motion blur to Fusion, optionally delegates DOF through the Fusion 21 OpenGL accumulation/depth-of-field inputs, and redistorts after Renderer3D with the same SynthEyes `DE4RadialStandardDegree4` LensDistort contract accepted by import. Brown k3, tangential distortion or a shifted optical center cannot be represented by that current contract and therefore reject package creation; there is no STMap or substitute route. RGB and matte use separate opaque 3D carriers and are recombined after projection so Fusion cannot interpret the matte as premultiplication. Final composition uses Fusion's registered `Custom` tools for explicit channel math `DeviceRGB + plateRGB × (1 − matte)` and never a conventional Over.

When a saved reference is included, the package carries Color's `studio-fusion-ocio-v2.4` configuration, not the application's ACES 2.0/OCIO 2.5 configuration. This explicit OCIO 2.4 subset contains only ACEScg and the declared direct reference IDTs. ACES 2.0 display/ODT views and OCIO 2.5 AMF/interoperability constructs remain application-only. A reference transform absent from the Fusion subset rejects queue creation before any files are written.

Every multi-file output owns one directory below the selected output directory; a single-file output writes the selected file directly. Collision validation occurs before the immutable job enters the queue. An existing single file or any file contained recursively by a sequence/package directory requires an explicit cancel-or-replace decision; an absent directory or a directory containing only empty subdirectories does not. The frozen policy is exactly `FailIfExists` or `ReplaceGeneratedFiles`. Replacement authorizes only the job's declared generated-file manifest and never clears or recursively replaces the destination directory.

Every arrow is a typed boundary. A consumer receives a complete validated result and never reconstructs the prior owner's semantics. Declared media color metadata crosses the Media boundary as typed evidence only. YUV matrix and signal range resolve independently from the Input Transform: `Auto` consumes only supported declared metadata, while absent or unsupported evidence blocks decoding until the user authors an explicit value. RGB sources bypass the YUV interpretation route, and monochrome sources require range but not matrix. The Platform adapter receives only a fully resolved decode interpretation and configures the single FFmpeg YUV-to-RGB conversion before OCIO. Color may propose an Input Transform from an exact complete pattern, while evaluation remains blocked until the source interpretation is explicitly authored.

Physical models publish stable ordered phase descriptors and typed parameter requirements from Rust. Application combines explicit preset capabilities and authored manual values into one immutable resolved request and prepares presentation descriptors from that request. A host UI renders those descriptors and returns stable control intents; it does not declare phase order, physical controls, numeric limits, units, preset compatibility, Color Mode availability or evaluator-intermediate mappings. Phase boundaries are named versioned artifacts rather than generic image-plus-metadata bags. ACEScg labels only explicitly scene-linear tristimulus boundaries; Feeder Signal, emitted radiance, sensor exposure and RAW retain distinct contracts. A model can be inserted between two phases only by implementing their exact typed ports or through an explicit separately owned adapter.

The physical evaluator and Application request are host-neutral. Desktop file or pattern acquisition and a later OFX input clip resolve into the same source-frame contract; Desktop preview/export and a later OFX output clip consume the same evaluated result. Host adapters own UI binding, source acquisition, render-context translation and output publication only. Exact time, frame rate, render scale, render window, pixel aspect, quality, spatial support and temporal input requirements cross explicit ports so tiled or multi-frame host rendering cannot select another physical route. Parameter identities are stable before host instance creation; runtime state changes availability and values, never invents model semantics in a UI adapter.

The native macOS shell has `Principal`, `Test` and `Settings`; it has no separate `Modelo` page or model-specific inspector. `Test` is the sole physical authoring and phase-inspection surface. Its renderer lives in the dependency-isolated `ScreenSimulationMacUI` Swift target and consumes only `ScreenSimulationPresentation` descriptors. Until Application/Rust publishes a valid phase descriptor, Test exposes no editable physical controls. Reintroducing a Swift keypath matrix or a host-authored phase list is a retired surface and an architecture failure.

Test begins with the host-owned source acquisition boundary: one external file or sequence, or one explicitly selected synthetic source. The source owner publishes interpretation evidence only. The Color-owned Input Transform section follows immediately with the current explicit authored selection; detected or proposed metadata may annotate an option but can never select it, supply an absent value or silently reconfigure decoding. Signal-model and range edits explicitly rebuild the decoder surface before publication. External and synthetic sources then enter the same linear ACEScg route. This source-and-color header is not a physical-model descriptor; it cannot declare a physical phase, device capability or model parameter. Physical controls remain absent until Application/Rust publishes their presentation descriptors.

Preview quality begins in host-only `Setup`, before Draft. Setup consumes the placed feeder signal, the active Device rectangle, the exact camera/screen poses, focal length, sensor gate and lens shift, and the authored Delivery Raster. It publishes only an ideal pinhole framing preview with a one-output-pixel red Device boundary; it does not evaluate panel response, cover, environment, lens aberrations/DOF, exposure, sensor or develop, and it never crosses the physical-render ABI. Any upstream edit invalidates a completed Draft/Media/High/Native result and atomically returns both the visible quality and image to Setup. A physical quality is evaluated again only when explicitly selected.

`Setup entorno` is a second host-only diagnostic quality. It projects the selected HDRI as a perfect 100% mirror through the authored camera and Device plane, without panel emission, cover transmission, roughness, anti-glare microtexture, lens aberrations, exposure, sensor or develop. The reflection remains at full strength inside the supersampled projected Device coverage and remains visible at a fixed 20% presentation gain outside it, solely to preserve spatial context while positioning the environment. It retains the same one-viewer-pixel red projected Device boundary as Setup so the reflection is positioned against the exact camera-visible screen area. This diagnostic dimming never changes the selected HDRI or the canonical Cover/Environment result. MMB translates the finite sphere in camera-local axes, Option-MMB changes the authored X/Y Environment rotation and Shift-MMB or the wheel changes its physical radius. The same rotation, projection identity, world-space centre and radius feed the canonical Cover/Environment evaluator.

The workstation also exposes `Crear reflejos`, an inverse environment-authoring tool layered over the normal camera/reference `Setup`, not over the HDRI-only `Setup entorno`. It therefore preserves a loaded reference behind the projected Device and requires no prior Environment asset. It does not paint the final frame or introduce another Cover evaluator. The user places circular practical emitters with center/radius handles, convex window/door quadrilaterals and a distant sun over the camera-visible Device. Geometry converts those handles into environment directions; Application validates the vector light rig and compiles it into one explicit 2:1 non-negative linear-ACEScg radiance raster; Platform encodes that raster as OpenEXR in the managed Environment library. Only the explicit `Generar y usar` action selects the generated EXR through the same `environment-image` input as any external HDRI. Practical-emitter and window distance derives a plausible physical emitter size from the authored angular extent, but a standard HDRI retains no per-emitter parallax or independent depth. The distant sun owns angular diameter rather than distance. Closing the tool preserves the generated asset and normal environment selection while removing its editing overlays.

`Encuadrar HDRI` is a second inverse-authoring tool for an already selected image environment. It shows the source panorama as a planar crop over the projected Device and exposes pan, zoom and roll around the Device centre. On the explicit `Generar y usar` action, Geometry uses the current camera and Device plane to invert the ideal mirror mapping, Platform writes one new linear-ACEScg 2:1 OpenEXR, and the workstation selects it through `environment-image`. Existing source rotation is baked and then reset together with finite-sphere projection, so the generated map has one unambiguous distant-environment placement. This is a calibration for the current pose rather than a screen-space lock: later camera or Device changes naturally sample different directions from that HDRI. The operation never changes Cover/Environment, never paints the final frame and never adds an angular-scale parameter to physical evaluation.

`Setup foco` is a third host-only diagnostic quality. It intersects the authored camera rays with the rigid Device, evaluates the current thin-lens circle of confusion from focal length, f-number and resolved focus distance, and displays maximum focus as white with a continuous falloff toward black. A red Device-local chart is clipped to the active Device and passes through the same radial/tangential distortion as the camera model. Its one-viewer-pixel red Device boundary is a sampled distorted curve rather than a four-line pinhole quadrilateral. When Autofocus is active, a green cross-and-ring gizmo identifies the required normalized Device-local focus target. Plain LMB places or drags that target through the exact inverse Delivery-Raster and Brown-Conrady projection; camera navigation and the Device transform remain unchanged. The same target follows animated camera and Device poses and resolves a new optical-axis focus distance at every frame. The diagnostic changes no optical checkpoint and camera navigation remains available without leaving Setup foco.

Setup is also the live surface for direct camera placement. MMB pans the camera, Option+MMB orbits on one locked Device-local axis, Shift+MMB dollies and the wheel performs the same physical Dolly; none changes focal length or the Device transform. Pan and Orbit follow the projected Device under the cursor, so their internal camera translations/rotations use the inverse sign. Pointer changes are coalesced to one latest pending pose; mouse-up cancels that pending publication, delivers the final pose directly and prevents old motion from draining afterward. Trackpad and Magic Mouse momentum is presentation inertia rather than authored physical input and is discarded. During a gesture the host may publish a proportionally reduced Setup raster using the exact Delivery Raster projection and boundary; it does not rebuild presentation descriptors or numeric controls. The host presents each completed interactive texture immediately even while AppKit is tracking the mouse, so image and boundary cannot use different poses. Mouse-up materializes the final pose once into the same Geometry selection displayed by Test, creates one Undo operation and republishes full-resolution Setup. Numeric edits immediately redraw Setup. LMB/pinch and the toolbar remain presentation-only pan/zoom and cannot alter the camera. A dedicated Viewer-navigation controller owns only presentation fit, zoom, pan and one-to-one state; `WorkspaceModel` composes it but cannot reinterpret those values as camera pose or physical authoring.

The red Setup boundary is a viewer-space diagnostic overlay, not image data. Its stroke is one logical viewer pixel after Fit, zoom and pan, and it is excluded from checkpoints, monitor output, saved frames and recording. Setup and the Viewer-only Reference composite supersample the projected Device silhouette after the authored lens distortion, so an oblique or curved edge has subpixel coverage without filtering the accepted physical checkpoint or its interior detail. `Cristal y entorno` publishes a host action for selecting an explicit equirectangular 2:1 HDRI/OpenEXR resource. The selection requires a scene-referred Input Transform, positive cd/m² per source unit and finite exposure EV; decoding and the IDT complete before the typed Environment radiance artifact is prepared. Changing back to a procedural preset releases the selected image environment explicitly.

Every saved-frame PNG embeds one strict current `ScreenSimulation.FrameSettings.v24` snapshot. It carries the complete Device, physical pipeline and contribution model together with the resolved Test selection: source interpretation and placement, camera/capture-raster/lens identities, Preview quality and cumulative phase, delivery raster, Recording Output and Codec settings, and the Preview transform used to inspect the result. An image Environment records its file name, SHA-256 identity and explicit scene-referred Input Transform while its radiometric scale, X/Y rotation, world-space sphere center/radius and exposure remain in the physical pipeline snapshot; the PNG never embeds or guesses the external HDR raster. The native macOS adapter imports selected maps into the content-addressed library at `~/Library/Application Support/SCREEN-SIMULATION/Library/Environments/HDRI`, opens the browser at that stable location and resolves saved hashes there. A reference image or movie is an independent input presented in its own left-panel card. The adapter copies it into `~/Library/Application Support/SCREEN-SIMULATION/Library/References` and records its SHA-256, explicit Input Transform, alpha interpretation, signal model, YUV matrix, signal range, placement relative to the Delivery Raster and four ordered Delivery-Raster-pixel targets; it rejects import when the exact asset or any required interpretation is absent. Reference placement is explicitly one of `Fit`, `FillCrop`, `Stretch` or `OneToOne`; letterbox regions remain outside the reference raster rather than being inferred as image content. A loaded reference remains the Viewer background until it is explicitly removed; this composition is Viewer-only and cannot modify checkpoints, monitor output or rendered files. A reference movie is the explicit timeline-duration and frame-rate authority while loaded, and the Device source is sampled at the resulting project time. Opening the floating Match panel disables physical camera navigation and exposes red crosses for the current rigid projection plus four directly draggable yellow TL/TR/BR/BL targets joined by a yellow quadrilateral. Moving one target never moves another; releasing it runs the calibrated four-point solver, which updates only the camera, reports reprojection error and cannot deform the Device. Closing or hiding the panel removes all Match overlays and restores normal physical camera navigation without removing the reference or discarding target coordinates. Plain MMB pans the Viewer and Shift-MMB, wheel or pinch zooms it without changing camera intrinsics or pose. Selected import is atomic and accepts only this current contract. It restores every authored render setting, reference identity, interpretation, placement and target coordinate. Source pixels, monitor profile, Viewer zoom/pan, transport, floating-panel visibility and job state are deliberately outside the saved-frame snapshot.

The native macOS left sidebar has a standard hide/show control and a vertically split scene shelf above the active inspector. Saving a scene creates one strict `ScreenSimulation.SavedScene.v13` workstation snapshot plus a presentation-only thumbnail. The snapshot contains the current saved-frame settings, exact current frame, exact rational frame rate, Viewer fit/zoom/pan and either the exact synthetic-pattern identity or SHA-256 identities for every external source item. External source files are copied into `~/Library/Application Support/SCREEN-SIMULATION/Library/Sources`; scene records, thumbnails and their strict index live in `~/Library/Application Support/SCREEN-SIMULATION/Library/Scenes`. A generated reflection environment is owned by exactly one saved scene and has the stable identity `scene-<scene-id>.exr`: editing the reflection rig overwrites that one map and updates its hash, never appends a new map. Duplicating a scene copies the generated map into a new scene-owned identity; deleting the scene removes its owned map. The unsaved working state has one separate `working-reflections.exr`. Opening resolves source content by hash and then applies the authored render snapshot; a thumbnail, filename, nearby file or preset can never impersonate a missing source. When a required external Device-source asset is absent, Open succeeds into the explicit `MEDIA MISSING` source state described by the snapshot: its stored width, height, frame count, rational frame rate, duration and authored color/alpha interpretation remain authoritative, and a conspicuous generated plate replaces only unavailable decoded pixels. Missing Environment, reference or SynthEyes Fusion tracking assets still reject Open because they participate directly in the physical or Viewer-reference contract. Rename changes only the shelf label. Duplicate creates an independent scene and resource ownership. Update and Delete require confirmation; Open also requires confirmation because it replaces the active scene. The normal scene reader accepts only the current schema and never converts on startup. A later schema revision requires an explicitly selected, one-way maintenance migration that produces and validates the complete new scene library before the new reader opens it. Render Queue is invoked from the saved scene's contextual menu. If that scene is active and differs from its stored snapshot, the workstation requires an explicit Update before enqueueing; an unsaved working state cannot enter the queue. Before destination selection, a required options sheet resolves composition, range, output preset/format and physical motion-blur sampling. Enabled motion blur replaces only the immutable job's shutter temporal-sample count while preserving the saved shutter interval and animated camera, Device and emission; disabled motion blur resolves exactly one sample and never applies a later 2D blur. Its resolved output configuration selects `Solo Device` or `Device + referencia`: the latter samples the saved reference at the same exact frame time and composites it only after the camera-rendered checkpoint and saved Delivery Raster, so reference pixels can never enter a physical phase. The native output queue is a separate narrow controller: each job owns an immutable copy of the complete saved scene, any scene-owned generated Environment bytes and its resolved output configuration, and evaluates them in an isolated workspace so later opening, updating, renaming or deleting a scene cannot redirect the job to the visible workspace. It also owns sequential execution, progress, cancellation and terminal state. `WorkspaceModel` prepares the job but cannot own or reinterpret the queue lifecycle.

Imported SynthEyes Fusion tracking scenes are content-addressed under `~/Library/Application Support/SCREEN-SIMULATION/Library/Tracking`. The floating `Tracking 3D` panel requires explicit camera and point-group selection, exposes point-cloud and auxiliary-geometry visibility independently, and lets each auxiliary mesh be hidden separately. When Fusion scene units are not declared, the user selects points A and B in the Viewer and enters their known separation; Geometry alone resolves metres per source unit. Until that succeeds the cloud can be inspected in its imported camera, but neither its camera nor geometry enters the physical request. A resolved animated camera drives the same Free camera state and focal/gate values as manual authoring at the current frame. Its point cloud is first projected in the exact raster of the loaded tracking plate, then that raster is placed once into the independent Delivery Raster with the authored reference-placement policy. The camera preset's photosite raster never replaces the tracking raster for this projection. Activating the Fusion camera clears prior lens shift and distortion, then applies its typed DE4 radial-degree-four calibration; a missing or all-zero calibration is exact pinhole and an unknown or contradictory model is rejected. Polygon faces retain their authored cardinality, so quads remain quads at the import and Viewer boundaries and are triangulated only internally when a renderer requires triangles. Saved Scene v9 stores the exact asset identity, role selections, visibility and two-point calibration; missing tracking media or an incomplete scale rejects Save/Open.

The current Test descriptor publishes twenty-three ordered cumulative phases. `Origin` ends at the versioned linear-ACEScg raster. `Source Adjustment` consumes that exact raster and applies authored exposure, contrast, saturation, temperature and tint in extended scene-linear ACEScg while preserving alpha and values outside zero to one. `Feeder Output` consumes that exact graded artifact, applies one independently authored Output Signal transform and places the resulting signal into the selected target Device raster with explicit Fit, Fill/Crop, Stretch or One-to-One semantics. Fit and Fill/Crop are mathematically identical when source and target have the same aspect ratio; the placement identity remains distinct and no artificial difference is introduced. A new selection is seeded from an equivalent display-referred Input Transform when one exists and is thereafter authoritative and independent. The strict nonlinear RGBA16F color checkpoint names the Input Transform, Output Signal and resolved feeder processor; it is the immutable input to placement, while the phase publishes the placed feeder-signal artifact. `Device Mapping and Interpretation` consumes that artifact and interprets its codes through the selected Device Color Mode, EOTF and editable White Luminance. The device's internal scaler is identity in the current version because the feeder already delivers the selected native raster; a future non-identity device scaler requires its own explicit model and phase. Changing Color Mode cannot recode the feeder color checkpoint. `Panel Structure` applies native subpixels and black matrix. `Panel Uniformity` then applies the Device-owned fixed manufacturing and compensation residual in physical panel coordinates; its map is signal-dependent but remains invariant under camera, placement and frame time. `Panel Light Spread` consumes that accepted uniform-panel-radiance artifact and applies the Device-owned calibrated spread profile. `Panel Temporal` consumes only `spread-panel-radiance-v1`, analytically integrates the resolved emission over the authored capture interval and publishes `temporally-integrated-panel-radiance-v1`. `Relative Geometry` consumes only that temporal checkpoint and resolves the selected camera, the independent camera/screen transforms and their physical separation as a typed data checkpoint without inventing a display raster. Its `Look At` mode authors camera distance and orbital orientation X/Y around the screen while always targeting the screen center; its `Free` mode authors camera and screen translation XYZ and rotation XYZ independently. Switching modes converts the current resolved pose instead of jumping to an unrelated seed. `Cover and Environment` consumes that geometry to evaluate incidence, transmission and reflection. `Device Emission Glow` consumes only the already resolved, placed and alpha-attenuated panel emission. It applies a bounded four-lobe separable-Gaussian VFX filter above an authored panel-white threshold, adds bloom inside the Device and publishes additive RGB with zero matte outside the active outline. Its millimetre radii follow camera projection; it never reads the original source, reference plate or Environment and never preserves sharp subpixel structure in the exterior halo. `Lens and Projection` selects one camera-compatible objective and applies the explicit Autofocus/manual policy, resolved focus distance, authored f-number, projection and its complete physical approximation. `Exposure and Shutter` integrates the image-plane illuminance over the authored exposure time, shutter behavior and ND. The same physical duration is presented as an editable shutter angle at the effective project cadence and as its synchronized reciprocal speed in `1/s`; neither representation is a second exposure authority. `Computational Capture` consumes that canonical integrated exposure and materializes an explicit bracket before Sensor. One exposure is exact single-capture identity; two to eight exposures add successively shorter highlight-protection captures at the authored EV spacing. The current VFX approximation evaluates optics once and represents the bracket as aggregate sensor capacity, so exposure count does not multiply optical render cost. It never applies a hue-specific look or tone curve. `Photosite/CFA Collection and Noise` consumes that effective exposure, selects the authored Bayer channel and publishes deterministic collected charge with shot/dark noise plus deferred read noise. `Sensor Bloom` consumes only that collected charge and publishes coupled charge after calibrated four-neighbour crosstalk and nonrecursive overflow transfer. `Sensor Readout and RAW` consumes only the coupled charge and applies full-well clipping, read noise, analog gain and ADC quantization to publish the final noisy mosaiced RAW. `Develop and Demosaic` consumes that RAW and publishes the developed linear ACEScg camera result. `Camera Rendering Intent` consumes only that accepted result and applies the selected capture preset values for exposure, contrast, saturation, temperature and tint to publish the final linear ACEScg camera-rendered artifact. It cannot alter RAW, choose an output transform or encode a recording. `Device VFX Transparency` consumes that accepted camera result together with the alpha sidecar transported from placed feeder signal. It publishes `device-vfx-composite-v1` as premultiplied additive Device RGB plus its occlusion matte; `ignore` resolves full physical Device coverage and `device-transparency` uses authored source alpha for the complete Device, including emission, pixel structure, moiré, cover, reflection, glow and optics. Reference composition consumes this contract directly as `DeviceRGB + plateRGB × (1 − matte)` and never reconstructs visibility in Swift. `Delivery Raster` consumes that exact artifact. `Recording Output` consumes the accepted delivery artifact and applies the Color-owned transform required by the selected recording profile to publish `recording-output-signal-v2`. It remains an explicit diagnostic checkpoint, not a second normal authoring choice. `Recording Codec` consumes only that signal and the authored Recording profile/character, executes the host codec adapter and publishes `decoded-recording-signal-v1` plus exact encoded-byte count and payload hash. Every capture preset explicitly declares its usual recording profiles and one default; Application marks those as habitual while still offering the complete codec catalog. Selecting another camera changes the default profile but never hides the other profiles. The decoded result is transformed back to linear ACEScg and shown through the same independent monitor Preview transform as the camera result. Sensor dynamic range remains owned by capture/exposure/develop; recording authoring does not expose a generic SDR/HDR switch or display a log signal unless that look is already present in the photographed source content. Codec-only changes reuse the accepted physical checkpoint; Output changes invalidate both downstream artifacts; upstream authoring invalidates all three. Application/Rust publishes all controls, effect summaries, header-control ownership, options, limits, slider steps, reset targets and the convention `0 = no effect`, `1 = calibrated physical` and `>1 = creative extrapolation` only where applicable. Every numeric slider spans twenty equal logical steps without visual tick marks while its adjacent numeric input accepts any in-range value; reset restores the owning preset default or the explicit seed for non-preset authoring. Character remains editable in the card header when its details are collapsed; Swift does not identify character fields or write phase summaries. The host renders each phase as an aligned expandable card and offers the same ordered phase identities in `Ver hasta`; selecting any phase sets its exact cumulative evaluator intermediate, including the explicit Origin checkpoint. The independent Preview ODT follows the inspected result. A checkpoint that lies outside that ODT's representable range remains authoritative even when its Preview clips or hides values; presentation never introduces an artificial normalization or visibility transform.

The current environment model publishes neutral, studio-softbox, calibration-grid, office-ceiling, daylight-window, warm-practical and mixed-production analytic linear-ACEScg patterns and an exclusive image-backed equirectangular source port identified as `environment-image`. The latter requires one finite exact single-level 2:1 ACEScg radiance texture plus explicit source-unit radiance, exposure EV and panel-local X/Y rotation. Test authoring exposes both rotations and exposure independently from the linear creative Environment character multiplier; selecting a procedural source releases the image source explicitly. Rough image reflection is integrated directly from that source with view-dependent GGX visible normals, dielectric Fresnel and Smith masking; deterministic multiple-importance sampling combines the GGX distribution with a solid-angle-weighted luminance distribution prepared from the exact source. The private distribution hierarchy contains sampling weights only: reflected radiance is always fetched from the unchanged level-zero map. It never substitutes an angular blur pyramid, fitted halo or analytic source. Device Emission Glow keys each accepted Panel Light Spread emission sample by panel-relative luminance before filtering, then evaluates one smooth multiscale approximation of an exponential halo with one authored physical radius. It preserves the original emission and adds only the keyed soft RGB contribution inside and beyond the active panel outline while leaving the matte unchanged. Its explicit `Spill exterior` control multiplies only additive RGB as the resolved Device matte falls away: zero removes external spill, one preserves calibration, and values through four make the same smooth tail perceptibly longer without changing its radius, key, interior bloom or matte.

Computational Capture represents its bracket as aggregate sensor capacity plus `floor(log2(exposure count) × Character)` effective fused-quantization bits, capped at sixteen. The effective precision belongs to the combined result and does not redefine the sensor preset's physical ADC; exposure count still does not multiply optical render cost.

The Sensor Bloom card exposes the selected camera preset's neighbour-crosstalk fraction and nonrecursive overflow-transfer fraction. They remain Sensor-owned physical parameters, resets restore that preset's exact authored values, and changing the camera replaces both atomically with the newly selected profile.

Media sample selection consumes exact project time and one authored policy. Rational timestamps compare by value even when the project and stream use different denominators. `Exact` requires an equal presentation timestamp and does not extend source edges. `Floor` selects the latest timestamped frame that does not exceed project time; `Nearest` compares the adjacent timestamps exactly and selects the earlier sample on a tie. Both non-exact policies explicitly hold the first or last sample when shutter or rolling-readout evaluation crosses the edge of a bounded source. Missing timestamps and unknown-duration access beyond the exact initial sample fail explicitly. There is no implicit policy change, retry, loop mode or legacy sampling route.

A new Test selection starts `Ver hasta` at the final phase published by Application. The physical request owns one parameter revision and hash; adopting another source raster or frame, changing its interpretation or placement, selecting another cumulative physical phase, or editing a physical parameter invalidates its completed frame through that single authority. Swift does not reconstruct or compare a second request identity for presentation. Native progress never presents 100% while the worker remains active: the host publishes the validated result texture and ends the observable task lifecycle before presenting the green current state.

## Technology

The current macOS-first implementation uses Rust 1.97.1 behind the SwiftUI/AppKit composition root in `apps/screen-native-macos`. Native RAW development runs through the required Metal backend on Apple Silicon; the physical core and typed domain boundaries remain platform-independent, but the current version does not require, ship or validate a Windows/D3D12 adapter. Native display publication uses one required Metal backend generated from the pinned OCIO processor and quantizes its result directly to RGBA8; the OCIO CPU processor remains only a numeric oracle with the explicit tolerance in `native_compute.md`. A Native cancellation remains an active job until the Metal worker confirms the cancelled terminal state; the host exposes that interval as `Cancelling`, retains progress from the last completed tile and cannot submit another Native job meanwhile. Media has two capability-selected Platform adapters: AVFoundation for media it declares playable and one bundled FFmpeg configuration for a codec AVFoundation declares unsupported. Both return the same decoded RGB contract after the persisted source matrix/range has been resolved; neither chooses an Input Transform or introduces an alternate Color route. The product color implementation is the extractable `packages/StudioColor` boundary copied from the authoritative CREDITOS-HDR OCIO/ACES implementation at the pinned source commit and hashes. The native host authors an explicit Input Transform into linear ACEScg, resolves the independently selected Output Signal into the nonlinear feeder contract, applies the Device Color Mode only in panel interpretation, calls the Rust-owned physical evaluator once per immutable request and uses the StudioColor OCIO-generated Metal display processor for preview and output. The local packager builds only `dist/Screen Simulation Native.app`, bundles and validates the complete FFmpeg dylib closure under `Contents/Frameworks` with app-local rpaths, and validates the current physical ABI. There is no packaged Rust/Slint product, runtime backend selector or compatibility shell.

The product's physical-frame boundary is the versioned coarse ABI in
`ScreenPhysicalBridge.h`, specified by `Docs/NATIVE_PHYSICAL_FRAME_CONTRACT.md`.
It carries one selected frame through an opaque input containing the source
linear-ACEScg texture, the nonlinear Device RGB texture resolved by StudioColor
and one explicit raster-placement policy. An immutable resolved Device snapshot
then crosses ordered Screen and Capture domains to one opaque linear-ACEScg
result texture. Screen consumes Device RGB and placement; Capture consumes the
physical Screen result. Rust/Metal owns physical stage semantics; Swift owns
only request orchestration and presentation state.
Preview, ColorSync, DeckLink and render output transforms remain downstream of
this boundary and cannot appear as physical contributions.

The current supported system is Apple Silicon on macOS 14 or later. Windows and D3D12 are outside the current version and impose no parity requirement on Metal work.

Domain packages expose narrow capabilities and do not depend on sibling implementation details. The exact allowed Rust package edges are executable in `architecture/domains.json`, and the exact Swift target edges are executable in `architecture/swift-domains.json`. Executable and host adapters are composition roots. The native macOS host translates its boundaries into immutable Application requests; a later OFX adapter must do the same and cannot introduce another evaluator, domain semantics or UI types into the core. Application publishes and resolves the ordered physical contribution set by stable stage identity, control semantics and dependency; host bridges cannot index that array to rediscover named phase meaning.

## Current scope

`Delivery Raster` follows Device VFX Transparency and precedes Recording Output. It consumes `device-vfx-composite-v1` and publishes `delivery-acescg-raster-v1`, preserving scene-linear ACEScg while establishing explicit output width, height, aspect-preserving `Fit`, aspect-preserving centered `Fill / Crop`, or centered `1:1` placement, and transparent or black background. Application publishes the explicit UHD, DCI 4K, HD, DCI 2K, vertical, square and current-camera-raster presets. Selecting one materializes all of its values; editing any delivery dimension, placement or background changes the authored identity to `custom` without inferring a preset from matching values. It never changes gate, lens, sensor, exposure or camera look. Recording Output and Codec consume only this accepted delivery artifact, so delivery-only or codec-only edits reuse the camera checkpoint.

Every Test phase publishes its native calculation-domain label for `Ver hasta`. The visible image remains a presentation of that authoritative checkpoint through the explicitly selected Preview ODT; the label never claims that the monitor directly displays native linear, radiometric, charge or RAW values.

Capture presets publish exact `Full`, `Half` and `Quarter` raster modes. `Half` denotes approximately half the total photosite count rather than halving each axis. The selected mode becomes the effective sensor raster before physical evaluation without changing gate dimensions or lens geometry. Each capture preset also publishes one explicit default Lens evaluation model: the iPhone 16e uses the continuous VFX 2D footprint and ARRI ALEXA 35 uses the direct 32-ray physical pupil. Selecting a capture preset atomically restores that default, while `Lens and Projection` exposes the resolved model as authored state instead of inferring it from quality, resolution or camera identity during evaluation. The iPhone 16e defaults to 5712×4284 `Half`; ARRI ALEXA 35 defaults to 4608×3164 `Full`.

The project-owned physical state includes complete LCD, optical-cover, environment and sensor profiles. Cover and environment cross the same immutable Application request as panel and sensor; they are not workstation-only effects.

The current implementation target is one source clip per simulation shot, one authored rational project frame rate, one project-owned complete LCD profile and sensor profile, internally authored independent camera-transform, camera-intrinsics and screen-transform tracks, an RGB/BGR stripe panel, transformed physical projection, deterministic reference sampling, a public linear optical result, exact global/rolling-shutter integration with analytically integrated residual flicker and optional banding, mosaiced RAW capture, debug views and still export. The immutable physical request also carries a typed host render context: complete-raster dimensions, a bounded render window, exact rational X/Y render scale and exact rational pixel aspect. The present evaluator explicitly supports only the complete window at unit scale with square pixels; other valid contexts fail as unsupported instead of selecting a different route or being silently ignored. The technical desktop also authors seven explicit bundled test sources: an animated checkerboard, a static black-on-white eye chart, a 3840×2160 editorial page containing common document/UI text sizes, a 3840×2160 photographic camera-color reference containing diverse skin tones, textiles, neutrals, glossy/matte materials and fine texture, a deterministic 3840×2160 frequency reference containing a Siemens star, authored 1–8-pixel line pairs, slanted edges, channel ramps and exact pixel marks, a procedural photometric scale containing nine achromatic device-signal patches at exact codes `0.00`, `0.05`, `0.10`, `0.18`, `0.25`, `0.50`, `0.75`, `0.90` and `1.00`, and the exact 3840×2160 ASUS framebuffer photographed in the controlled iPhone VFX comparison, including browser chrome and authored page scroll. That VFX source explicitly selects `OneToOne`, so one source pixel reaches the matching ASUS device pixel without the invalid enlargement of the earlier cropped raster. Their device-signal channels remain in `[0,1]`; none is a media fallback. The four raster references are decoded once into the same prepared device-signal representation used by media, while every procedural reference enters the same device-signal, placement, panel, optical and native-capture evaluator without an image-decoding route. A source whose raster differs from the device native raster requires one authored placement policy: `Fit`, `FillCrop`, `Stretch`, or `OneToOne`. Pixel decode matrix, pixel decode range, source IDT and alpha association are independent explicit decisions. Alpha association is resolved before panel evaluation, while its scalar value remains a non-color placed-feeder sidecar for the independently authored Device VFX Alpha Mode.

The technical desktop camera-result view authors one complete capture profile: native photosite raster, physical gate, Bayer pattern, sensor response/noise/ADC data, one lens-association policy, one explicit default lens id and a nonempty compatible-lens set. The bundled templates are ARRI ALEXA 35 Open Gate, an explicitly labelled calibrated approximation of the iPhone 16e main camera, and explicitly labelled reference approximations for Canon PowerShot A470 plus iPhone 14 Pro main and ultra-wide validation cases. Every optic, including an integrated handset module, lives in the single Geometry-owned lens catalog. The ARRI declares the compatible generic 18, 25, 35, 50, 85 and 135 mm approximations and an interchangeable policy. Fixed cameras declare only their matching integrated/reference lens and do not emulate computational photography. Selecting a camera and compatible objective copies their separate complete values into current state, and evaluation never resolves a preset id. Focal length, distortion, chromatic behavior, vignetting, transmission, softness and veiling-glare fraction come only from the selected lens, never from a duplicate camera field. Reference approximations expose unpublished geometry, full-well and radiometry as assumptions rather than calibrated facts.

Within `Lens and Projection`, the micrometric PSF core and the wide-field veiling-glare tail are
separate authored quantities. The current tail redistributes a bounded fraction toward the covered
panel's gate-average linear irradiance before exposure. It is not cover-glass glow, sensor bloom or
a field-dependent ghost model.

An explicit one-frame native capture may evaluate either the complete sensor or a centered native 1024×1024 region. Both use the same optical, RAW and development route. Evaluation is partitioned into 128-pixel sensor tiles without first materializing a giant luminous-panel raster. Every ray retains complete-sensor coordinates, rolling-shutter row time remains anchored to the complete sensor, and media is decoded and cached at every exact temporal sample requested by that tile rather than frozen at nominal frame time. The panel signal remains at its native device resolution with one immutable summed-area representation per resolved media sample. Sensor CFA phase, counter-based noise identity and panel-cell phase are therefore global: a regional result is exactly the same pixels as the corresponding crop of a complete capture. Demosaic evaluates its complete three-photosite support around each requested region before cropping it, so tile boundaries cannot create another result. Tile execution occurs off the UI thread, reports progress, supports cancellation between complete tiles and publishes the authoritative frame only after completion; the host samples progress at no more than 20 Hz and republishes observable values only when they change, so technical UI observation cannot contend with Native computation. A downscaled staging visualization may expose completed tiles without becoming an output. The worker also derives a deterministic three-level 2× area-filtered display pyramid from the completed developed frame. The workstation viewer selects among that pyramid and the unchanged native level according to magnification: Fit cannot resample the full sensor texture directly, while `1:1 Sensor` presents the native level at one sensor sample per logical viewer pixel. These display levels are non-authoritative and cannot become capture or export data. The neutral-gray viewer draws one fixed one-point outline around the exact displayed raster after Fit, zoom and pan, so the frame boundary remains distinguishable from its surround. Zoom and pan never change camera geometry, focus, optical sampling or the authored result. Physical inspection remains a separate camera operation and is unavailable as a substitute for viewer magnification in the camera-result view.

The workstation has one explicit quality selector: `Draft` targets a 360-pixel-wide preview, `Medium` 960 pixels and `High` 1920 pixels; `Native 1024 px sensor crop` and `Native complete frame` select exact sensor capture. The final discrete preview width may differ from its quality target by one pixel so the integer height and width represent the authored viewport within the required half-pixel bound. The three preview qualities use the identical camera, lens, depth-of-field, panel and full-gate projection; only the explicit output sampling raster differs. In optical diagnostic views they use the explicit presentation-only Preview EV. In Camera Result they instead approximate the authored capture exposure and ODT while explicitly omitting the sensor/RAW stages enumerated by the sensor-capture contract. They never change the selected view. Ray projection continues to use the exact authored viewport aspect and the viewer presents that aspect, so this is raster quantization rather than another camera or gate policy. A larger mismatch remains an error. While one preview is running, UI changes invalidate its publication and coalesce into one subsequent render at the selected quality instead of creating parallel semantic routes. Native modes never render implicitly: one contextual `Render` button appears beside the fixed quality and camera selectors, and cancellation remains explicit. A completed non-stale Native result may be exported as one output-transformed 8-bit RGBA PNG by encoding its unchanged level-zero publication buffer. Export neither reevaluates the scene nor consumes a display-pyramid level, and its selected output transform is named in the workstation result. That display-referred still remains distinct from the Render Queue's explicit scene-linear ACEScg OpenEXR contracts and cannot be used as their input.

The inspector groups the adjustable physical stages in their execution order: panel emission,
subpixel structure, panel spread, relative camera/screen geometry, cover plus incident environment,
lens, then the discrete CFA and demosaic boundary. Panel and lens
amounts use the same authoring convention as cover and environment: zero is the corresponding ideal
identity, one is the calibrated profile and values above one deliberately extrapolate character.
These amounts are parameters of the same CPU/Metal optical request and invalidate Native results;
they do not select alternate renderers. CFA and demosaic remain discrete because a continuous amount
would not describe a physical operation. Intermediate-buffer taps are intentionally not claimed until
the current immutable results expose those boundaries.

Panel Structure owns `Contraste de estructura`, which controls how strongly the explicit fixed-pixel carrier and black-matrix structure differs from continuous panel emission. Lens and Projection separately owns periodic-versus-continuous sampled-interference intensity, residual-chroma saturation and optical antialiasing. At zero intensity Lens removes that low-frequency interference while preserving the visible fixed-pixel carrier, spread and glow from the accepted Panel Structure chain; at one it preserves the calibrated sampled result. These controls cannot act as a source grade or change panel white luminance.

The bundled LCD device catalog is a set of current authoring templates with stable ids, native raster, active physical dimensions, one reference operating white with an explicit basis label and one default optical-cover authoring template. Selecting a device copies both complete profiles into current state; it never leaves a runtime dependency on either catalog id. The white and cover selection remain editable. Evaluation never looks up a preset id, and an existing project result therefore cannot change when the bundled catalog changes. Generic templates state that their white is an authored approximation; the ASUS ProArt PA329CV uses its published 350-nit typical SDR value and the 14.2-inch MacBook Pro template uses its published 500-nit SDR value. `Custom` edits the same complete values and does not select another evaluator. PPI, diagonal and pixel pitch are derived presentation values, never independent authorities.

The optical-cover catalog provides glossy, semi-gloss, matte and thick-glass approximations. Its complete material profile authors thickness, refractive index, anti-reflective efficiency, RGB absorption, roughness and haze. A separate environment source supplies either one analytic distribution or one equirectangular HDR radiance raster. Values are scene-linear and may exceed one; EXR decode does not choose color, and the authored Input Transform converts the decoded samples to ACEScg before the physical request. Image-backed radiance has an explicit cd/m²-per-source-unit calibration and exposure in stops. The desktop exposes independent non-negative character amounts: cover amount zero is an exact identity and environment amount zero contributes no reflection, while values above one explicitly exaggerate the same operators. Cover evaluation is shared by Draft, Medium, High and Native capture.
